# 실제 업무 자동화 바이브 플로우

## 목적

과정 68~70에서 배운 웹훅, LLM Agent, Switch 라우터, Execute Workflow 모듈, 규칙 검사, 버전 관리를 실제 사내 업무에 적용한다. 요청문은 먼저 입력·흐름·결과 계약으로 정리하고, 에이전트가 JSON을 만든 뒤 `check`와 테스트로 검증한다.

## 공통 개발 흐름

```text
업무 요청과 기대 결과 작성
  → 같은 흐름과 종류별 설정 분리
  → 공통 규칙을 Sub-workflow로 분리
  → Agent/라우터 JSON 작성
  → flow.py check
  → n8n push
  → cases 테스트와 실패 보고서 확인
  → 영향 표 갱신 후 커밋
```

## 실제 업무 사례 5개

### 1. 사내 공지 자동 작성·검사·게시

- 입력: `kind`, `facts`, `request`
- 흐름: Webhook → 종류 설정 표 → Writer Agent → 규칙 검사 모듈 → 게시 결과
- 종류: 점검, 보안, 교육, 설문
- 검사: 날짜·시간 누락, 개인정보, 최대 길이, 필수 문장, 외부 링크
- 결과: `{kind, route, published, notice, codes}`
- 재사용 포인트: 종류별 머리말과 제한값은 `Kind settings` 한 곳에서 관리한다.

### 2. 긴급 공지 SMS 발송

- 입력: `facts`
- 흐름: Webhook → SMS Agent → `modRuleCheck01` → 전송 또는 담당자 확인
- 규칙: 80자 이내, 날짜·시간 보존, 전화번호·메일·링크 제외
- 결과: `{sms, published, codes}`
- 재사용 포인트: SMS 전용 규칙을 모듈 안에 하드코딩하지 않고 `max_length=80`을 입력으로 넘긴다.

### 3. IT 문의 멀티 Agent 라우터

- 입력: `message`, `user`, 선택적 `title`, `notes`
- 흐름: Split Agent → 업무별 index 부여 → type Switch → IT/회의록 Agent HTTP 호출 → Merge/Aggregate → 정렬된 결과
- 결과: `{count, results, reply}`
- 장애 처리: Agent가 400·404·500을 반환해도 해당 업무를 `담당자 연결` 결과로 바꾸고 다른 업무 결과는 유지한다.
- 재사용 포인트: 각 Agent의 입력·출력 계약을 고정한다.

### 4. 회의록에서 후속 업무 만들기

- 입력: 회의 제목과 원문 회의록
- 흐름: 회의록 Agent → 요약·결정·할 일 추출 → 담당자와 기한 확인 → 업무 관리 시스템 전송
- 결과: `{summary, actions: [{owner, task, due}]}`
- 검사: 회의록이 없으면 Agent를 부르지 않고 입력 요청을 반환한다.
- 재사용 포인트: 회의록 형식 검사를 별도 모듈로 두어 이메일·업무 관리 도구에서 함께 사용한다.

### 5. 출장비 정산 자동화

- 입력: 사용자, 출장 기간, 영수증 목록, 금액
- 흐름: Webhook → 비용 분류 Agent → 규칙 검사 모듈 → 승인 라우터 → 회계 담당자 또는 자동 승인
- 검사: 필수 영수증, 출장 기간, 금액 상한, 개인정보와 외부 링크
- 결과: `{total, items, route, published, codes}`
- 버전 관리: 금액 초과를 즉시 차단하던 v1에서 경고로 바꾸는 경우 `modExpenseCheck02`를 새 ID로 만들고 기존 승인 흐름은 v1을 유지한다.

## 바이브 코딩 요청문에 반드시 넣을 것

- 저장 파일과 웹훅 경로
- 입력 필드와 필수 여부
- 노드 순서와 Agent를 부르는 조건
- 최종 JSON 필드와 오류 응답
- 공통 규칙과 종류별 설정의 위치
- 기존 사용처와 회귀 테스트 파일
- `flow.py check` 후 사람이 실행할 `push`, `test` 명령

## Claude 실행 메모

Claude에게 요청할 때는 아래 순서로 전달한다.

1. `AGENTS.md`, `SPEC.md`, 관련 테스트 파일을 먼저 읽는다.
2. 현재 워크플로우 계약과 영향 받는 사용처를 표로 확인한다.
3. 변경 전 기대 결과와 수정할 노드를 분리해 적는다.
4. 기존 JSON 구조를 유지하면서 필요한 노드만 수정한다.
5. `uv run tools/flow.py check`와 관련 회귀 테스트를 실행한다.
6. 결과 보고에 테스트 보고서 경로와 남은 위험을 포함한다.

### Claude 요청문 예시

```text
AGENTS.md와 my-work/SPEC.md를 읽고 시작해.
먼저 현재 계약, 영향 받는 워크플로우, 테스트 파일을 표로 정리해.
my-work/notice-kit.json에서 필요한 노드만 수정하고 계약 필드는 유지해.
모듈 버전 변경이 필요하면 기존 ID를 덮어쓰지 말고 영향 표를 갱신해.
check와 관련 회귀 테스트를 실행한 뒤 결과와 실행 명령을 보고해.
```
